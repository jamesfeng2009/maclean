## #41 W-11 Windows 资源嵌入（图标 / manifest / 版本信息）

踩到并解决的三个坑：
1. `embed_resource::compile()` 返回 `()`，**没有 Result**。非 Windows 宿主找不到
   编译器时是**静默 no-op**（不报错也不 panic）——最危险的失败模式。
   对策：编译后按 crate 命名契约自查 `{OUT_DIR}/{file_stem}.lib` 是否存在，
   不存在就打 `cargo:warning` 说明"交叉编译产物不可用于发布"。
   Windows 宿主上 compile 内部会 panic，天然就是 CI 硬门禁。
2. msvc 目标在 macOS 上只认 `llvm-rc`（不认 windres）；设 `RC_<target>` 环境变量
   可强制指定。装 `mingw-w64` 后本机就能真编译 .rc 验证语法。
3. `VERSIONINFO` 字符串在资源里是 **UTF-16LE**，manifest XML 是 ASCII。
   用 grep 找 "sunge.men" 永远命中不了 —— 差点做出一个永远红的 CI。
   CI 校验改用 pwsh 分别按 ASCII / Unicode 解码后再查。

brew 的一个坑：`brew install mingw-w64` 第一次报退出码 0 但实际没装上
（`brew list` 显示 Not installed），要复查 Cellar 而不是信退出码。

## 双平台功能盘点（2026-09-19，纯调研未改代码）
方法：源码里 **0 个 TODO/FIXME**，标记没写在代码里，改用三条硬证据反推缺口——
① `cargo clippy --target x86_64-pc-windows-msvc --all-targets` 的 dead_code 清单
（= macOS 有、Windows 没有的自动清单，27 个符号）；
② macOS 目标 dead_code（0 条，说明 macOS 侧接线完整）；
③ 文本 grep 生产调用点（区分"写了函数"和"真被调用"）。

结论分三类：

**Windows 侧缺口（macOS 有）**
- 应用保护分级缺失：`check_bundle_protection` 只在 `uninstall.rs:535` 被调（macOS 路径），
  `WindowsUninstallScanner`/`uninstall_app` 全程不调 → Windows 卸载无 Critical 拦截。
- 安全软件识别缺失：`get_security_vendor`（`app_protection.rs:174`）生产调用点只有
  `uninstall.rs:571`，也是 macOS 路径。
- 多磁盘扫描**写了但零调用**：`set_scan_all_disks` / `should_scan_all_disks` /
  `list_available_disks` 都在 `windows_apps.rs`（cfg(windows) 模块），Windows 目标上是
  dead_code，UI/设置页/CLI 全无引用 → 默认只扫 C 盘，D 盘装的开发工具扫不到。
- APFS 页签是空壳：`Tab::all()` 返回 9 个 Tab **不按平台过滤**，`apfs.rs` 也没有
  cfg 门控 → Windows 上照样显示该页签，跑 `tmutil listlocalsnapshots` 必然失败返回空列表。

**macOS 侧缺口（Windows 有）**
- 卸载不调官方卸载器：macOS 侧若命中 `RequiresOfficialUninstaller` 只是标记
  `protection_official_uninstaller:{vendor}` 拒绝删除并提示，不代调卸载程序；
  Windows 侧有 `uninstall_win32` / `uninstall_uwp` / `uninstall_uwp_winget` 真执行。
- 无系统级回滚点：Windows 有 `ensure_restore_point` / `backup_registry_key` /
  `restore_last_backup`（已接线，ui 5470 附近，受 `settings_auto_restore_point` 控制）；
  macOS 只有废纸篓。

**两平台共同缺口**
- 付费分级只有"500MB 累计清理额度"（`check_quota_allow` / `FREE_CLEAN_QUOTA_BYTES`），
  全仓 grep `is_pro|Plan::|pro_only` **零命中** —— 没有任何 pro 专属功能门控。
  `plan` 字段（lifetime/yearly）只用于显示，不控制功能。
- 自动更新只到"查版本 + 跳下载页"（`updater.rs` 仅 `check_latest()`），无下载/校验/安装。
- 无定时或计划清理（只有 60s 的磁盘占用刷新）。
- CLI 只有 5 个子命令（scan/clean/check-disk/list/log），纯文本表格输出，
  无 JSON，无法脚本化集成。

方法沉淀：盘点"还有哪些功能没实现"时，若源码无 TODO 标记，**用交叉编译目标的
dead_code 告警当自动清单**最省力也最可靠，但必须再用 grep 确认"是否真被调用"——
dead_code 只证明没被调用，不证明是缺口还是平台不适用，两者要人工分开。

### 本轮反复踩到的坑（下次直接照做）
1. **`clippy -D warnings` 是最好的"接线检查器"**：backup.rs 写完 9 个 pub 函数，
   clippy 立刻报 6 个 dead_code —— 那就是"写了没接线"的自动清单。
   修法不是加 `#[allow(dead_code)]`，是把它们接到 CLI/UI 上（本轮接到了
   `maclean backups` / `maclean restore` 两个子命令）。
   确实只在另一平台用到的，才用仓库已有的
   `#[cfg_attr(not(target_os="windows"), allow(dead_code))]` 并写明理由。
2. **`include_str!` 源码断言会自我指涉**：断言"源码里不含 X"时，测试自己的字面量
   也会被算进去，断言永真。必须先 `src.split("\n#[cfg(test)]").next()` 切掉测试模块。
3. **中文源码不能按字节切片**：`&s[..200]` 会 panic（踩到多字节字符边界），
   用 `s.chars().take(200).collect::<String>()`。
4. **源码断言别钉缩进**：钉死多行字符串会被单纯的格式调整打断，那是噪音不是回归。
   改成"断言两个标记都在 + 相邻"。
5. **Edit 工具本轮多次静默失败**（报 success 但文件没变，至少 6 次）。
   涉及编译正确性的改动，**改完立刻 grep/sed 校验**，不要连着改一堆再编译。

### 有意为之的诚实边界（都是写进模块注释的）
- M-2 不假装能系统级还原：永久删除的字节回不来，清单只记事实，UI 照实显示"0 项可还原"。
- C-2 不做静默自替换：自替换运行中的 exe 在两个平台上都不稳妥，需要另起 updater 进程。
  现在是把安装包交给系统打开并告知用户还要做什么。
- C-3 没有"每天 20:00"这种时刻设置：std 拿不到可靠的本地时区偏移，
  为此引入 chrono 不划算。现状是"每 N 天到期即跑"。
