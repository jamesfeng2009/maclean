# 2026-09-20

## 修 CI 1.98 新增的 clippy 告警（commit 571bb33）

用户贴了 CI 的 clippy 报错（unnecessary_sort_by ×3、filter_next ×1），本机
`cargo clippy -D warnings` 却是干净的。

**根因：CI 用 `dtolnay/rust-toolchain@stable`，工具链版本会漂移。**
本机 rustc 1.90，CI 已是 1.98 —— 8 个版本的 lint 差，所以告警只在 CI 红。
1.93 也跑过，同样干净，说明这些 lint 是 1.94~1.98 之间新增的。

修的内容：
- `backup.rs` 两处、`updater.rs` 一处：`sort_by(|a,b| b.x.cmp(&a.x))` →
  `sort_by_key(|a| std::cmp::Reverse(a.x))`
- `residual_match.rs`：`filter(..).next_back()` → `.rfind(..)`，语义等价
  （rfind 对 DoubleEndedIterator 即从后往前找首个满足项）
- 顺手修掉一个假测试（见下）

## 方法沉淀：工具链漂移下的 lint 修复

1. **别猜 lint 会不会报，装同版本工具链实测。**
   `rustup toolchain install 1.98.0 --profile minimal --component clippy`
   然后 `cargo +1.98.0 clippy --all-targets -- -D warnings`。
   跨 Windows 目标还要 `rustup +1.98.0 target add x86_64-pc-windows-msvc`。
   本机默认版本干净 ≠ CI 干净，这条以后每次都要记住。

2. **预防性改动必须反向验证。**
   我看 `logger.rs` 的 `sort_by(|a,b| b.0.cmp(&a.0))` 形状一样，就顺手改成了
   `sort_by_key(|a| Reverse(a.0.clone()))`。改回去实测：1.98 **不报**
   （`a.0` 是非 Copy 的 String，clippy 不会为非 Copy key 建议 sort_by_key）。
   这一改反而白加一次字符串分配，已回退。
   教训：形状像 ≠ 会被报；预防性改动前先反向跑一次。

3. **`include_str!` 源码级断言会自命中。**
   测试里写 `src.matches("std::cmp::Reverse")` 会把自己写的字面量也数进去
   （license.rs 之前踩过一次）。解法：按测试模块切分源码
   `src.split("\nmod tests").next()` 再断言。

## 假测试：在测试里重写被测逻辑

`backup::tests::listing_sorts_newest_first` 原先在测试里自己写一遍
`v.sort_by(|a,b| b.created_at.cmp(&a.created_at))` 再断言 new 在前 ——
这只验证了标准库，`list()` 的排序改坏了它也照样通过。

修法：把排序抽成纯函数 `sort_newest_first(&mut [BackupManifest])`，
测试改为调用它；再加一条断言排序规则只有一处实现（防止有人绕过）。

**反向验证**：把 `Reverse` 去掉改成升序，两条测试同时变红 —— 证明真在测生产代码。

## 待办 / 建议（已提给用户，未做）

CI 的 `dtolnay/rust-toolchain@stable` 会持续漂移：任何一次 Rust 升级都可能
让 CI 在你没改代码的情况下变红。建议固定版本（`rust-toolchain.toml` 或
workflow 里写死）。等用户决定，未擅自改 CI 配置。
