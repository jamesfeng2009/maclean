## 本轮最重要的教训：`#[cfg(target_os)]` 模块的假覆盖

我把 X-1/X-2 的纯函数和 test 写进了 `windows_apps.rs`，该文件是
`#[cfg(target_os = "windows")]` —— **本机 `cargo test` 显示 0 passed / 149 filtered out**，
即一个都没编译。而 `cargo check --all-targets` 照样全绿，看着像过实则零验证。

正确做法：**把待验证逻辑挪到不限平台的新模块**（不是放进 cfg 模块内部再想办法）：
- `src/scanner/residual_match.rs`（供 windows_apps 使用）
- `src/platform/reg_safety.rs`（供 windows_backup 使用）
两者都加 `#![allow(dead_code)]`（本机非 windows 构建下无调用方）。

判定法则：**任何 Windows-only 文件里的修正，必须跑
`cargo check --target x86_64-pc-windows-msvc --all-targets` 才算验证过**，
本机 check 通过不代表这事干完了。

另一个指标：写进 cfg 模块的 test，本机 `cargo test <名>` 会显示
`X filtered out` 且 0 passed —— 看到这就是信号，别当成用例没写对。

## 其它工具/流程坑

1. **同一文件的两次 Edit 不要并行发出**：本轮并行发了两个 Edit 到
   residual_match.rs，一个生效一个静默丢失，导致后续反复修括号（浪费 4 轮）。
   同文件多处修改请在一条命令里做完，或串行调用。
2. Edit 的 new_string 必须自带闭合括号：我两次漏写 `}` 导致 "unclosed delimiter"。
   之后可用 python 脚本算括号深度快速定位。
3. 测试断言要尊重真实实现：我一度按"我以为是的行为"写了 3 条断言，
   全红后才看清是自己对 Google/Goo、JavaSoft/保护名单的预期错了。
   红的时候先确认是代码错还是断言错。
4. include_str! 源码级检查会命中**自己写的注释**：我的注释里带
   `search_name.contains(&dir_name)` 字面量，把检查自己打红了。写检查项时注意措辞。
5. docker `system df --format` 是 **3 列**（Type/Size/Reclaimable），
   照源码注释里那张可读表格写测试数据会多一列、取到 SIZE 而非 RECLAIMABLE。
